# Product

`UnEmployed` is one local-first desktop app with two modules:

- `Job Finder`
- `Interview Helper`

## Shared Baseline

- shared local profile, documents, reusable answers, and application history
- shared browser runtime, source intelligence, AI provider roles, desktop shell, settings, tray, and hotkeys
- UI-first workflows with agent assistance inside bounded product surfaces

## Job Finder

Target authority model:

- Job Finder will support `prepare_only`, `confirm_before_submit`, and
  `autonomous_submit` modes under an explicit user-scoped authority envelope.
  Autonomous mode is a core product capability and may complete final submission
  when the saved policy covers the exact application and action. Unknown facts,
  security challenges, unavailable credentials, and actions outside the policy
  still pause rather than being guessed. See ADR 0012.
- The checkout described below is still the prepare-only implementation baseline.
  No existing flag, IPC call, or legacy mode is reinterpreted as submit authority.
  The browser/application architecture is under review and may be replaced before
  autonomous execution is implemented.

Current baseline:

- The normal user flow is numbered and sequential: (1) Profile, including first-use setup and resume evidence review; (2) Find jobs, which searches enabled sources using the saved profile and search settings; (3) Shortlisted, which reviews selected jobs and prepares optional tailored drafts; and (4) Applications, which records and prepares each application without final submission. Needs you, Task center, and Settings support this flow but are not extra steps in it.
- Job Finder navigation keeps the four flow destinations visible as Profile, Find jobs, Shortlisted, and Applications. At CSS widths of at least 1440px, a persistent 17rem sidebar shows the grouped destinations. Below that breakpoint, the compact top navigation provides the four flow destinations and a `Planning & settings` menu for the remaining destinations.
- First-use Profile setup offers Light edit, Balanced rewrite, and Strong rewrite as tailoring defaults. Strong rewrite can substantially rewrite, combine, or elaborate only supported experience; every generated line remains reviewable, and Job Finder does not invent facts or numbers, auto-approve, or submit applications.

- resume import and profile editing with guided setup and profile copilot; each new import saves a private working copy and records the SHA-256 of those saved bytes. The first-run privacy explanation distinguishes the local working copy from optional configured-model analysis, and setup never implies that model processing is purely local. Import locks profile/setup editing until reconciliation finishes so a late import response cannot overwrite a concurrent draft. Existing legacy source references are migrated into app-owned storage when their bytes remain trustworthy; missing, unreadable, or changed legacy files show a replace-resume recovery path without discarding extracted profile details and cannot appear application-ready. Extraction retains every grounded role and bullet, derives work mode only from candidate evidence, keeps skills role-specific, and supplements sparse provider output with deterministic grounded evidence instead of silently dropping supported history. Re-importing unchanged app-owned bytes can reuse local analysis only when parser, provider/model, prompt, schema, reconciliation policy, and candidate-context fingerprints all match; refresh actions intentionally recompute because they do not reread and re-hash source bytes. In the profile editor, a half-filled project, language, proof, or custom-answer row blocks saving with a message that names the row instead of being dropped silently, fully empty rows stay optional, duplicate collapse applies only to import candidates (manual duplicates are never removed), the Main skills field stays independently authoritative while full-skill consumers derive their own unions from Main plus skill groups, and role-family fields accept comma- or newline-separated tokens. One router-level guard asks a single composed confirmation before any in-app navigation (link, push, or back/forward) that would lose unsaved profile, setup, or resume edits or abandon an in-progress or failed save; the confirmation is an app-owned accessible dialog that names each unsaved scope and offers Stay on this page or Leave without saving instead of a native browser prompt; hash-only fragment jumps stay exempt. Closing or quitting the whole window with unsaved work asks one app-owned confirmation instead of a native prompt, and an approved discard covers exactly that close — any later unsaved change asks again. When profile content changes in the background while the editor holds unsaved edits, untouched fields adopt the saved changes while edited fields keep the entered values under a notice to review the merged fields; if a safe merge is impossible, an explicit conflict keeps the unsaved edits and requires an explicit save or reload before continuing
- compensation keeps two deliberate truths: the typed search range guides matching and may contain only a minimum worth considering, while the reusable expected-salary answer is separate application text that can name a higher preferred range. Matching normalizes saved and listed amounts to an annual equivalent when their explicit currencies match, so monthly, hourly, and yearly wording are comparable without constraining how a job advertises pay. Unknown or different currencies remain neutral because the product does not guess exchange rates. Leaving the search maximum blank never caps or hides better-paying work, and application use still pauses for review. Deterministic Profile Copilot salary commands respect the same truths: they stage typed compensation operations for exactly the bounds the user expressed, keep stated currency (£/€/$/ISO) and pay period verbatim, inherit only an explicitly saved currency, ask a narrow question with no patch when low amounts lack a period ("2k") or when bounds contradict saved state instead of silently clearing or reinterpreting the other bound, route `salary expectations answer` phrasing to the stored application answer rather than structured compensation, and never convert between currencies or periods
- Profile Copilot uses one schema-validated, review-first operation channel for all supported profile and search-preference edits, including scalar and list fields, structured records, removals, and review-item resolution. The runtime, not the model, owns proposal IDs, timestamps, and review state; chat cannot mark its own proposal applied. Explicit multi-field commands retain each field's own value, explicit `null` or empty-list clears are valid edits, and ambiguous clauses are omitted or clarified instead of borrowing a neighboring value. Apply, Reject, and revision-backed Undo remain separate user actions. Profile Copilot does not expose application submission or other external workflow authority.
- browser-driven job discovery across configured targets; setup and Find jobs share one readiness rule requiring at least one enabled valid public HTTP(S) source. The full Profile has a dedicated Job sources tab for large libraries: it summarizes enabled/disabled/attention state, searches and filters the complete catalog, renders only 25 compact rows per page, and mounts the detailed check/guidance editor for one opened source at a time. Importing, suggesting, or storing a source does not enable it; the user must explicitly opt in, and only enabled sources run. Normal discovery targets up to 100 useful candidates across configured sources, while an explicit single-source run targets up to 50 and uses bounded result-pane scrolling and pagination before slower selective review; captured result cards prefer scoped title, company, and location fields so high-volume discovery does not trade away basic listing identity. Explicit target roles remain editable guidance, but are optional: when absent, discovery derives an inspectable search scope from saved target roles, experience titles, headline, skills, preferences, and exclusions instead of blocking on a vague title. Disabled search controls explain and link directly to the missing source owner. Guided setup includes the same basic source name, URL, and enabled-state editor used by the full Profile flow, and cannot complete while no runnable source exists. Independent public provider inventories begin concurrently, fast public-provider source checks avoid unnecessary browser work, and title/location/work-mode triage plus distinct-role budgets rank useful options against the active resume and explicit or profile-inferred scope. Public Lever boards use the matching US or EU provider endpoint from their hostname. Compact collision-safe known-job aliases, versioned fingerprints, freshness deadlines, and provider update timestamps skip unchanged enriched work early while changed/reactivated listings refresh; one shared identity resolver prioritizes provider/source-scoped posting IDs and normalized employer application URLs, treats exact title + company + location + absolute date only as a possible corroborating alias, and refuses ambiguous or conflicting legacy aliases instead of silently selecting or deleting an unrelated posting; later sources budget from distinct newly retained identities so duplicate-heavy early sources cannot consume their exploration share. Every source result explicitly reports inventory completeness as complete, partial, or unknown. Only a complete source inventory can mark a previously known exact listing inactive; partial or unknown observations preserve uncertainty. Interrupted or all-source failed discovery becomes an explicit failed record while safe results and history remain intact; partial multi-source success retains completed work and identifies failed sources for exact retry
- an evidence-backed fit ledger that separates required, preferred, and inferred requirements; cites exact listing text and resume/profile sources; marks support, missing evidence, uncertainty, and conflicts; and keeps both the numeric score and conservative strong-fit/original-CV/review/skip recommendation grounded in that evidence. Scorer/session version 4 adds typed role suitability, preference alignment, application effort, evidence coverage, and compensation; orders conservative recommendation before aggregate score; rejects non-openings and unrelated role families; and treats geography, clearance, and thin required evidence conservatively. Unknown evidence stays neutral: a listing that names no concrete work mode beyond flexibility stays unknown rather than compatible in preference alignment, and unpreferred concrete modes listed alongside flexibility stay ambiguous instead of becoming conflicts; Easy Apply changes only effort, hard conflicts stay hidden by default, and the full requirement ledger remains inspectable. When a saved result is meaningfully reassessed or changes position in the visible ordering, Job Details preserves the latest change and explains it through a closed `Why this result changed` disclosure; unchanged refreshes do not erase that explanation. The shell reflows all six Job Finder destinations at practical native Electron 125% zoom at a normal desktop window — the current low-vision acceptance point after native 200% zoom was removed from current acceptance by user decision because it collapses into a mobile-like layout with low diagnostic value — while recommendation badges wrap inside their parent assessment cards
- source-debug that learns reusable target instructions from schema-safe DOM/text evidence and bounded visual evidence
- resume workspace with ATS-first preview, export, approval, template selection, manual experience ordering, explicit editor representation for every canonical work-history record, and an atomic pre-mutation version ledger capped at the newest 100 persisted revisions per draft; exact review-required restore survives restart, clears approval/export readiness, protects newer edits from stale saves or slow AI regeneration, and marks the restored draft as needing a fresh review before it can export again rather than presenting it as failed generation. Requested section rewrites are review-first like Guided Edits: regenerating a section produces a pending proposal bound to the current saved draft and changes nothing until the user explicitly accepts it, unusable model output yields a truthful no-change message instead of a fabricated patch, and model-proposed lines always carry assistant provenance so generated wording never presents as user-authored. New drafts use the exact target role as the headline, place supported job skills first, rank accomplishments and projects for the vacancy, suppress repeated metrics, and hide weak or unrelated history by default in balanced/aggressive modes while keeping every canonical role available in the editor. Conservative mode preserves compact career continuity. Aggressive mode substantially rewrites, combines, and elaborates cited evidence: it may spell out plausible engineering details around an evidenced stack (JavaScript, TypeScript, Next.js), product domain (restaurant management SaaS), and existing metrics, and experience/project bullets may cite profile-level skills as supporting evidence. The whole draft remains review-required, and hard facts such as named technologies and products, employers, dates, credentials, seniority, leadership, and any new number still require saved evidence; model-flagged inferred lines are counted in the draft notes so every inferred line can be checked before approval. Experienced profiles target two pages rather than forcing a crowded one-page document. All eight apply-safe templates use flat recruiter-grade typography, restrained rules and accents, and print-aware entry pagination rather than card-like document chrome; rendered HTML or PDF exports record the SHA-256 of the exact output bytes and preserve their exact format
- a persisted application-CV choice: Settings defines the default for jobs shortlisted later, while every shortlisted job keeps its own `Original CV unchanged` / `Tailor for this job` selection; changing one job never changes another current job or the Settings default, and Apply Copilot remains an explicit per-job action in both modes
- Shortlisted supports bounded sequential preparation of the next up to 10 eligible tailored drafts. A curated batch selection persists per active campaign across navigation, and staging the batch consumes that curated selection so returning to Shortlisted always shows the true pending set. Each draft still requires individual review and approval; this preparation never exports, approves, queues, submits, or sends drafts automatically.
- eight apply-safe templates: `Chronology Classic`, `Senior Brief`, `Modern Editorial`, `Engineering Spec`, `Proof Portfolio`, `Formal Proof`, `Longform Timeline`, and `Career Pivot Bridge`
- target-generic prepare-only apply flows that fill exact grounded profile fields, attach the explicitly selected original or tailored resume, advance only clearly non-final steps, and stop at final submission or any ambiguous gate; disposable acceptance runs may separately authorize intermediate ATS writes without authorizing or clicking final submit. Every catalog/browser execution path is normalized to `prepare_only`; legacy submit-capable modes pause without a submitted outcome or timestamp. Tailored approval and both original/tailored pre-apply paths reject missing integrity records, missing files, or SHA-256 mismatches before browser work; readiness names the exact CV, redacted destination, unresolved user work, allowed intermediate writes, and disabled final submit; afterward, each new result carries a redacted receipt and can export a local redacted JSON packet without credentials, raw browser state, URL secrets, or local file paths; receipt fields attest to Job Finder's own authority and actions rather than proving the site's outcome
- a unified, persisted `Needs you` Action Inbox with distinct login, signup, MFA, email-verification, CAPTCHA, account-choice, manual-answer, legal-consent, redirect, upload, and other presentations. Every classified application blocker persists. Authentication kinds verify source access; challenge/control kinds verify that the exact blocker is absent. Done schedules at most one run/job/result/checkpoint-scoped `prepare_only` retry: the same blocker stays blocked, no blocker resolves, and a changed blocker becomes a new pending request. Stable identity, claim/CAS/idempotency, restart, and multi-instance protections prevent duplicate execution; no request grants credentials, account creation, intermediate-write consent, or final-submit authority
- `Needs you` is visually and semantically separate from the sequential Profile → Find jobs → Shortlisted → Applications workflow, while Settings remains available with the workflow destinations
- discovery keeps Current Search in the same first-column position before and after results arrive; established layouts place Job Results in the center and Job Details on the right. The Job inspector always describes a job that is actually visible: when pagination, search, or sorting moves the selected result off the current page, the inspector synchronizes to the top of what is shown (and clears when nothing matches) instead of describing a row the user cannot see. Results sort deterministically by best match, newest listing-origin date, or company with a direction toggle; the choice persists locally and clear mismatches stay at the bottom under every pivot. Result rows and details retain source attribution and support source, workflow-status, listing-activity, work-mode, and fit filters. Listing activity is a derived snapshot fact, separate from workflow status: active comes from the newest verified/seen evidence, inactive from a complete source inventory, and stale/closed from typed listing signals. Inactive and stale are review warnings rather than proof of closure; an exact closed signal blocks shortlist and application preparation in the service as well as the UI. Result counts separate what a run collected from what remains retained and reviewable, and while a search streams in, the header reports what is actually visible after the persisted query and filters ("X of Y matches ready to review") instead of a raw total
- wide locked screens move the page header out of the way once, then send each ordinary mouse-wheel step to the scrollable pane under the pointer: an unmarked inner scroller inside that pane (kanban column lists, CV preview wells) consumes before its marked pane, text controls keep browser-owned scrolling, and each owner hands control outward at its boundary. Fractional header heights cannot trap the wheel, reaching a pane boundary hands control back to the outer page, and changing result pages resets only the result list while preserving the rest of the screen
- `Not interested` is an explicit local preference, not a ranking fact: users choose one or more bounded reason chips before hiding a result, hidden jobs remain reviewable in a disclosure, and `Show again and reset` restores the job and clears the feedback. Rediscovery preserves the explicit hidden state across stable aliases while accepting refreshed factual listing and fit evidence
- Search History preserves a typed per-run change digest for new, unchanged, changed, reactivated, inactive, known, and skipped listings, plus duration, warnings, and per-source health. Failed sources can be retried only through the existing single-source operation; history never turns retry into a broad replay.
- tailored-résumé generation exposes a readable labelled progress bar with its estimate outside the fill and keeps the same displayed progress when the user leaves and returns while that operation is still pending
- Resume Studio opens on the live preview and export/approval controls; job context and claim-level evidence stay available in a collapsed native disclosure instead of pushing the primary document task out of view
- Guided Edits stays in a solid floating viewport panel, defaults to the bottom-left, supports drag/maximize/minimize/close controls, clamps to the current viewport, and badges new replies instead of reopening itself or moving the underlying workspace. Each proposed change names its target location and offers a collapsed `Why this edit is grounded` disclosure that shows the nearest linked source excerpts and the saved claim assessment only when it still matches the exact current saved text; missing targets, refs, or validation degrade to explicit not-checked copy, and every disclosure states that proposed wording is checked after the user accepts and saves. Approved résumé state names the exact artifact and exposes one clear continuation back to Shortlisted
- Shortlisted exposes one state-driven primary application action above supporting evidence. Its label, enabled state, blocker, and nearby recovery action derive from the selected job and résumé asset, while uncommon proof and diagnostics remain available below or through disclosure
- a global Task center derives truthful stages, source/count progress, supported cancel/restart/review actions, and history-based estimates from persisted run state without a fake countdown
- cancelling application preparation aborts the active browser work instead of only changing the saved label, closes the app-owned working tab, and prevents late browser results from changing a cancelled run back to running. Closing the app waits for active preparation to stop; any still-running record is saved as failed with a clear restart path and an explicit statement that Job Finder performed no final-submit action. The same recovery runs after a hard process interruption so Task center cannot reopen with a permanent ghost task. Recovery also settles every still-planned result of such a run to a terminal failed outcome whose copy says preparation stopped before review and no final submit occurred: genuinely begun results keep their preparation-start marks and keep counting toward the daily begun-application limit, never-begun or legacy results record an explicit no-start instead of legacy uncertainty, results awaiting review or already finished are left unchanged, and rerunning recovery changes nothing further
- a bounded local product-action registry lets an assistant read workflow summaries, inspect Needs you and an exact apply run, create review-only Profile Copilot proposals, shortlist/dismiss/restore one job, or open one existing user-action page. Mutations carry explicit confirmation policy and typed receipts; proposal tools never auto-approve, and no tool can submit, create an account, navigate arbitrarily, read files, or mutate an external application
- meaningful edits expose saving/saved/failed state with stale-completion protection, exact retry, guarded navigation, and restart receipts; high-churn workspace updates can arrive as revisioned slice deltas with stale/gap rejection and one-shot full-snapshot recovery
- résumé imports can propose evidence-cited timeline repairs for overlaps, gaps, ambiguous or reversed dates, split/duplicate records, and missing employer/title; every proposal is independently accepted, rejected, or undone with stale-edit protection
- manual application answers distinguish one-use storage from an explicit future Profile save. Suggestions show provenance, prior question, confidence, scope, and revision; they are never inserted automatically and conflicting saved answers are never overwritten
- Documents is a dedicated secondary destination for resumes, cover letters, portfolios, work samples, transcripts, certificates, and images; Settings links to it instead of embedding the library. Imports are copied into app-owned storage, signature/MIME and size checked, SHA-256 verified, and shown to the renderer as metadata only. Each asset carries sensitivity, retention, and an explicit private-storage, application-attachment, or assistant-context consent scope; importing an asset does not automatically attach it to an application or expose its bytes to a model. `until_deleted` remains the default, while 30- and 90-day policies are explicit choices whose clock starts only after import succeeds. Removal or expiry makes an asset unavailable immediately and moves it to Trash for seven days; restore requires an explicit policy and starts a fresh clock, after which ordinary filesystem deletion purges the stored file and metadata. Supporting-file uploads obtain bytes through a main-process-only loader that rechecks lifecycle, consent, size, and SHA-256 immediately before the browser file control is filled, so later removal or tampering blocks the upload. This is recoverable product deletion, not a forensic secure-erase guarantee
- Applications can create a cover letter or short-response document for one exact application and optional file question. Deterministic generation ranks approved profile summary, proof-bank, experience, project, and skill evidence against the exact job and question, removes repeated evidence, and composes a concise proposal from at most three evidence blocks; the preview exposes every excerpt. File-question generation requires current exact run, result, question, job, and ApplicationRecord lineage and fails closed when that lineage is stale or crossed. A user can edit the proposal and save the text only as a new compare-and-swap revision. Edited revisions are marked user-authored and require claim review because their changes are not automatically grounded. Approval is revision-specific, copies the exact text into Documents & assets with the accurate `cover_letter` or `application_response` type and application-attachment consent, and still requires the user to select and save it for the exact file question. Export is a separate local `.txt` action. None of these actions grants account-creation or final-submit authority
- Settings can export a strictly allowlisted local diagnostic JSON containing build/capability/timing/warning summaries while excluding credentials, raw résumés, transcripts, audio, screenshots, browser storage, and private payloads

### Campaign command center and application tracker

- Every workspace has one durable active search campaign. Existing workspaces receive a default campaign without losing their jobs, sources, history, applications, or review work. Precision mode starts with a small high-quality target; Scale mode starts with a much larger retained pool and controlled preparation batches. Both modes remain editable rather than hiding fixed presets.
- A campaign owns its roles, locations, work modes, exclusions, compensation, sources, fit threshold, retained-job target, preparation limits, resume policy, progress, and history. Find jobs, Shortlisted, and Applications show the active campaign. Workspace-wide search can still find an item from another campaign and switches campaign before opening it.
- Job Search Home is the command center. It shows persisted counts, source health, active work, follow-ups, interviews, response rates only when a real denominator exists, and one derived next action. It also has the active-campaign selector, workspace-wide local search, and the global browser/application pause.
- Results, Shortlisted, Applications, Needs you, Search History, Documents and assets, campaign lists, and resume version history have local search with result counts and no-match states. High-volume surfaces keep selection and filters stable, support keyboard movement, and use saved density/views or columns where those controls are useful.
- Applications has a local CRM with Discovered through No response stages, table/Kanban/calendar views, a timeline, reminders, interview dates, contacts, notes, Candidate Asset attachments, compensation and offer details, tags, custom stages, duplicate hints, and CSV/JSON export. The configurable no-response rule defaults to 14 days. Preparation approval timeline entries describe opening/filling for preparation only, including legacy entries, and never imply submit approval. Externally observed stage changes use a blocking confirmation modal that isolates background focus, traps keyboard traversal, closes on Escape/backdrop cancel, and restores focus to its opener. Marking an application Applied or later is a manual tracking fact only; it never grants browser submission authority or invents a submission receipt.
- The global pause prevents new discovery, source-check, and application work and stops active owned work while local review and editing remain available. Campaign stop rules pause a preparation batch for configured login/signup blockers, changed or unexpected forms, unresolved human-answer or eligibility uncertainty, and an abnormal blocked/failed rate after its minimum sample.

The six phase-two slices below are implemented in the current checkout and have
the historical focused verification recorded in `docs/TESTING.md`; additional
focused workers extend that coverage. The current dirty candidate remains active
and unaccepted until the exact-source production gate and hardened Electron
acceptance checks recorded in `docs/STATUS.md` are green.

- Campaign rules are enabled/disabled `Must have`, `Prefer`, and `Never` rules over the evidence-backed job fields. Hard exclusions stay separate from ranking preferences; each rule shows its provenance and freshly measured remove/downgrade/unknown counts against the campaign's real retained jobs. The pre-search funnel is derived only from those real jobs — a campaign with no retained jobs yields a zeroed funnel instead of any invented estimate.
- Local schedules are enforced: run-now, daily, and selected-weekday runs respect time-zone-aware start times, pause windows, campaign limits, and the existing safe stop conditions; every finished run updates persisted run facts. A campaign digest persists new, changed, reactivated, inactive, known, skipped, and failed-source outcomes, and local in-app notifications cover strong new matches and blocked/failed campaign work. No external email or push integration exists.
- Outcome analytics record only explicit user-controlled outcomes on applications and slice them by campaign, source, job title, company, and resume strategy with real sample sizes, visible uncertainty, and conservative, inspectable, resettable suggestions that never change objective job facts. Recording rejects ambiguous identity: a job in multiple campaigns requires the campaign identity, and a job with multiple application records requires the application identity; the selected identities are persisted with the outcome. Recording `Applied` remains a local tracking fact and never creates submission evidence.
- Named role-family resume strategies carry a base resume, template, headline/skills/coverage policy, tailoring strength, evidence boundaries, campaign default, and a per-job selection with an inspectable reason. Automatic role-family recommendations and per-job selection are enforced. Strategy resolution passes the selected policy, including the base document and headline, skills, coverage, tailoring, and evidence boundaries, into résumé generation; reuse never approves, readies, or un-stales an artifact. A campaign default remains persisted when its strategy is disabled; the strategy screen keeps that disabled default visibly represented with an explicit clear action, while disabled strategies cannot be newly assigned.
- Search plans are optional reusable discovery settings for separating roles, sources, discovery volume, rules, and progress; they do not configure or authorize application volume. The current default plan is enough to start finding jobs. Discovery filter, sort, and view selections persist per plan, so switching plans cannot leak selections between plans. Application preparation instead has fixed product safeguards of at most 10 unique employer jobs per run and 20 begun employer applications per local day across campaigns and legacy lineages. The dashboard separates exact usage from uncertain legacy capacity and shows the next local-midnight reset. Resume approaches are optional reusable role-family rules reached from Shortlisted job context: a job uses an explicitly chosen approach, and when the job has no explicit choice its search plan can name one enabled approach as a fallback recommendation; assignment and reuse never approve or make an artifact application-ready.
- Company intelligence pages keep the complete company-linked saved-job collection, including openings hidden from the active discovery result set, plus applications, outcomes, contacts, notes, salary/offer evidence, source history, and preferences. Exact canonical names and user-approved merge aliases can own jobs; legacy aliases and domains cannot. Domains remain corroborating/conflicting research evidence, and existing jobs are not destructively rewritten around domain guesses. Listing activity stays distinct from application workflow state. A stale company URL shows `Company not found`, selects no substitute, and offers a route back to Companies. Conservative duplicate handling surfaces near matches as explicit merge-review candidates that require a user decision.
- High-volume safeguards add per-company/time-window application caps, simultaneous-application conflict checks, stale/closed/suspicious listing signals, abnormal-failure pauses, quality-review sampling, contradictory-answer protection, reversible dismissals, and explicit recovery guidance — all local tracking facts that never grant submission, credential, or account authority. Technical discovery/source-debug and application-terminal failures create idempotent safeguard and in-app notification evidence, while explicit user-owned blockers such as login, consent, CAPTCHA, MFA, or manual steps are excluded from the technical-failure sample. Contradictory grouped answers persist idempotent advisory safeguard evidence even when a reusable decision is rejected. Analysis concurrency remains saved policy rather than a runtime cap.
- `Not interested` can optionally hide the exact job and add an exact-normalized-employer exclusion in one atomic mutation after a preview. The reusable exclusion is offered only when company identity is unambiguous; domain evidence may corroborate identity but never creates a domain-wide exclusion. Reversal removes only the referenced employer exclusion and does not silently restore or rewrite unrelated job feedback.
- Application records are exact application lineages, not one mutable row inferred from a job. Starting another application creates a separate record; apply results, attempts, questions, answers, artifacts, replay checkpoints, consent, Needs you requests, campaign projections, and grouped-answer actions stay bound to that record. Manual answers preserve their exact run/job/result/question/application lineage and provenance; reusable Profile saving remains a separate explicit choice.
- CRM single-record and bulk stage changes merge against transaction-current application records. Bulk changes carry every visible expected revision, commit all selected records or none, retain manual tracker provenance, require confirmation before claiming externally observed stages, and keep failed selections available for explicit retry with a visible error. Company salary evidence must name its exact current job; offer evidence must also name the exact ApplicationRecord. Failed evidence saves retain the user's draft for correction instead of clearing it.

Current implementation rule: live submit remains disabled while the new authority
architecture is unimplemented. Current application runs keep
`submitAuthorized: false` and `accountCreationAuthorized: false`; the final
application control is never clicked. This is a migration state, not the target
product ceiling. See [ADR 0012](adr/0012-user-scoped-autonomous-application-authority.md).

## Interview Helper

Current baseline:

- target-context setup from Job Finder records or direct user input
- rehearsal checks for transcript language, runnable audio/transcription paths, providers, screenshots, assistant responses, and retention defaults
- capture consent is capability-specific: a user can run system-audio-only, microphone-only, or screenshot-free sessions after accepting the core transmission, retention, and visible-surface disclosures
- a visible main-window conversation with explicit text sends, temporary PNG/JPEG/WebP attachments, screen-capture context, assistant replies, and a recent source-labeled transcript
- user-started microphone and meeting/system-audio transcription with queued transient chunks, local-command STT or configured cloud fallback, native-caption intake, and cue generation behind typed provider roles
- live sessions start with an empty transcript and no synthetic cue; standalone Whisper non-speech markers and short recorder-tail fragments are discarded instead of becoming coaching context
- post-session review, export, transcript annotations, delete, and explicit Job Finder follow-up actions
- starting an interview opens visible answer and transcript popup windows by default while the main conversation remains available; the answer popup is a compact interactive assistant with typed sends, pasted or selected image attachments, explicit screen-context capture, answer copy, and hide/reopen controls, while the transcript popup stays optimized for live source text with copy and hide/reopen controls
- popup workspace updates are event-driven rather than renderer reloads so live audio/transcript changes cannot erase an in-progress answer draft or pending image attachment; popup position and size persist across sessions
- personal-story requests without candidate evidence produce a bracketed STAR scaffold instead of invented employers, incidents, technology, timelines, metrics, or outcomes; screenshot-dependent questions use model-backed visual observations when available and otherwise disclose that visual analysis is unavailable instead of guessing from earlier transcript context

- active sessions expose a derived Session health summary for microphone/system-audio signal, transcription backlog and fallback, cue latency and fallback, popup visibility, and the latest recoverable failure. It uses existing local session state, preserves the session on failure, and never writes back to Job Finder automatically\r\n\r\nHard rule: capture, screenshots, attachments, advanced overlays, and model use must stay explicit, visible, auditable, and adapter-owned. See [ADR 0003](adr/0003-interview-helper-live-session-architecture.md) and [ADR 0008](adr/0008-visible-first-interview-helper.md).

## Product Defaults

- desktop shell: `Electron`
- renderer: `React`
- local persistence: `SQLite`; desktop startup enables rotating database-only recovery snapshots on graceful close plus a separate pre-reset snapshot. These snapshots do not include generated resumes, Candidate Assets, application documents, or browser-profile files
- browser runtime: managed sessions first
- AI: provider abstraction with separate chat, vision, STT, and embedding roles
- configured generative routing uses OpenCode Go: `deepseek-v4-flash` through Chat Completions with requested `max` reasoning for ordinary text and tool work, and `gpt-5.6-luna` through Responses with `high` reasoning for image-only work. Audio transcription remains local Whisper or an explicit audio-capable model. See ADR 0010 for routing and ADR 0009 for the contract-first agent boundary.
